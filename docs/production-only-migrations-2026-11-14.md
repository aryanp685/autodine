## Classification key

- **SUPERSEDED (renumbered)** — same logical change as the named repo file (counterpart version recorded in the production ledger); effects verified or directionally superseded by later migrations.
- **SUPERSEDED** — console-era predecessor with no repo file; effects verified present/intentionally-absent; superseded by the repo migration sequence.
- **HAND-APPLIED, REQUIRED** — console SQL never in the repo; load-bearing for the running application; inventory only, never drop.
- **CONFIRMED APPLIED** — directly verified live (cron.job / absence-of-expected-object).
- **NEEDS INVESTIGATION** — recorded and partially verified; a specific attribute-level fact could not be established from the available read-only probes.

## Dependency order and replay safety

The table is ordered by version, which is also the production application order and the dependency order (schema → security → QR/session chain → billing/invoicing → brand → subscription-adjacent work). The repo migration replay (`scripts/reconcile/reconcile-migrations.mjs converge`) independently proves the repo chain applies cleanly on a populated database and that later migrations never require the 49 console files in order to run. Replaying ANY of the 49 against production is unsafe and unauthorized:

1. `create or replace function` entries would overwrite current (often intentionally-drifted) bodies — e.g. replaying `20261021124307 report_sales` reintroduces the unguarded export; replaying `20261106062054 storefront_settings` clobbers the current `begin_online_payment` state; replaying `20261107000107`-family receipt migrations re-arms receipt triggers against live payments.
2. Non-transactional DDL (`create cron job`, `drop policy ... if exists`) is not idempotent.
3. Several entries' exact SQL is UNKNOWN (never recorded in the repo; bodies not recoverable from md5). Any reconstruction would be a guess and is expressly out of scope.
