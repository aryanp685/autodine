## Executive assessment

The reviewed branch contains a database-enforced order-read boundary. Authenticated staff receive only operational columns from the base `orders` and `order_items` tables. Owner, Manager, and Cashier use explicit role-filtered finance views. Neither the operational grant nor the finance views expose the guest bearer `guest_token`; `anon` has no direct order-table SELECT in the migration candidate. Synthetic database tests verified role, tenant, column, view, publication, and cancellation behavior on a disposable embedded PostgreSQL instance.

Kitchen no longer reads or renders payment state or order totals. The previous Kitchen UI displayed a payment badge and monetary total; this is an explicit resolution of the standing requirement to deny Kitchen access to financial order fields. Kitchen tickets and waiter calls now refresh through role-scoped server reads every five seconds. Both raw source tables are removed from the `supabase_realtime` publication in the local migration candidate; the app no longer subscribes to their Postgres Changes payloads. This minimizes row delivery but changes waiter-call freshness from event-driven to a maximum five-second poll in the foreground.

The new SQL and app changes have been replayed and tested locally, not applied to any hosted project. Thus the repository-side blocker is addressed and regression-tested, while hosted migration parity and current Production grants/publication remain unknown. Do **not** describe Production as fixed, claim release readiness, or deploy on the strength of local verification.

## 2. Repository-side security changes

### Database order and line-item reads

Forward migration `supabase/migrations/20261112000500_role_scoped_order_reads.sql`:

1. Revokes table-level and per-column SELECT from `PUBLIC`, `anon`, and `authenticated` on `orders` and `order_items`, then grants authenticated staff only the operational fields needed by current readers. The base order grant omits payment state, all order amounts, cancellation internals, `order_session_id`, and `guest_token`; the line-item grant omits `unit_price_paise`.
2. Creates `orders_finance` and `order_items_finance` views with `security_barrier = true` and an explicit `has_restaurant_role` predicate for Owner, Manager, or Cashier. The views expose the needed finance columns and line prices but not `guest_token`. No anonymous SELECT grant is added.
3. Retains the existing tenant row policies; the role check is an additional boundary for finance. The cancellation RPC admits only Owner/Manager/Cashier for ordinary staff cancellation, returning a generic authorization error to Kitchen before checking payment state. Guest-token cancellation remains a separate path. After authenticating the caller, it explicitly calls `restaurant_can_write()` before a new guest or staff cancellation mutation; the security-definer function cannot rely on the ordinary write-gated RLS policy.
4. Preserves cancellation's session-before-order lock, guest ten-minute/new-state rule, idempotent already-cancelled result, pending-online-payment guard, paid/served refusal, and cancellation update. A read-only restaurant refuses new cancellation mutations, while an already-cancelled retry remains a no-op.

Follow-up migration `supabase/migrations/20261112000700_order_line_edit_boundary.sql` closes a related issue found during the independent review: the earlier SECURITY DEFINER line-edit RPC allowed Kitchen and did not enforce the restaurant write gate. The replacement preserves valid guest-token edits, limits ordinary staff edits to Owner/Manager/Cashier, checks the write gate after caller authorization and before payment-state guards, and returns a nonfinancial authorization error to Kitchen before it can distinguish pending-online, paid, or unpaid tickets. Disposable PostgreSQL regression tests cover the corrected paths.

Current app consumers are aligned to that shape: dashboard, bill, cashier list/action use finance views where required; dashboard top-item prices use `order_items_finance`; Kitchen, held-table summaries, and the Cashier's operational line list use nonfinancial base columns; the Cashier order ledger continues to select only safe operational fields. `lib/db/database.ts` now types base order/line rows as operational-only, records the finance views separately, and omits the restaurant plan/trial columns withheld by the subscription migration.

### Kitchen financial-data decision

Earlier UI/demo behavior showed `Unpaid · pay at counter` and an order total to Kitchen. This conflicts with the preserved security requirement that Kitchen cannot read financial order fields, even when the display is useful operationally. The chosen resolution is **no payment badge and no order total** for Kitchen. Both values were removed from the loader output, UI, demo fixtures, held-table summaries, and related UI/browser assertions. Kitchen still receives the dish, quantity, table, note, prep status, and necessary operational announcement data. If the product later requires an unpaid signal, it needs a separately approved, nonfinancial design; do not restore raw `payment_status` or amounts to the Kitchen role.

### Realtime minimization

The same migration removes both `public.orders` and `public.table_waiter_calls` from `supabase_realtime` (and fails closed if that publication is configured for all tables), then sets both relations' replica identity back to `DEFAULT` instead of `FULL`. Kitchen no longer opens a Postgres Changes channel; a five-second poll refreshes ticket and waiter-call data through the server-side role-scoped reads. This avoids relying on client filters as authorization and avoids serializing full order/payment/credential rows into those Realtime payloads. Direct `table_waiter_calls` reads remain tenant-scoped by RLS.

A repository-wide search for `postgres_changes`, channel creation/removal, and Realtime usage found no active application Postgres Changes consumer after the Kitchen hook and E2E subscription were removed. Remaining matches are historical migrations/generated staging SQL, unused monitor/alert helpers and tests, and documentation—not another order or waiter-call event consumer. The synthetic load helper also opens no channel; its polling requests use the fixture Owner token and are not a Kitchen-role load test.

This is a deliberate freshness tradeoff: calls no longer arrive instantly from this channel. The Kitchen screen says tickets and calls refresh every five seconds. Local catalog tests confirm those two tables are not in the publication after replay; hosted publication state and current hosted Realtime health are **UNVERIFIED**.

### Subscription history ceiling and Owner/Manager read boundary

Migration `supabase/migrations/20261112000600_cap_subscription_history_ceiling.sql` clamps the event- and payment-history RPC limits to `1..50` before JSON aggregation. Migration `supabase/migrations/20261114000100_owner_manager_subscription_reads.sql` preserves those clamps and deterministic newest-first ordering while narrowing billing reads to Owners and Managers.

The new migration restricts direct RLS reads of `accounts`, `subscription_events`, `subscription_payments`, and `subscription_receipts` to users with an Owner or Manager membership at an outlet on that account. The four billing-read RPCs—`account_subscription_state`, `account_subscription_history`, `account_payment_history`, and `account_receipt`—apply the same role check and return null to Cashier, Kitchen, guests, and nonmembers. History tests insert 60 synthetic rows, request 500, and confirm the newest 50 in stable order for both allowed roles. Direct table and RPC probes cover Owner, Manager, Cashier, Kitchen, anon, and a nonmember.

Legacy per-restaurant `restaurants.plan`, `plan_status`, `trial_started_at`, `plan_started_at`, and `plan_expires_at` remain for compatibility but are not directly selectable by any API-facing role, including Owners and Managers. The account-level `accounts` row is the client-facing source of commercial state, available directly only to Owners and Managers. The guest storefront projection does not include plan/trial fields.

The other plan readers were audited as well. `restaurant_access()` is a SECURITY DEFINER, membership-checked RPC and now returns plan/status/trial/account/outlet presentation only to Owners and Managers; Cashier and Kitchen retain exactly `can_write`, `read_only`, and `features`. `restaurant_trial_ends_at()` is Owner/Manager-only. `account_trial_ends_at()` remains SECURITY INVOKER and inherits the narrowed `accounts` RLS policy. The current `20261114000100` definitions make `account_outlet_count()` and `restaurant_features()` SECURITY DEFINER with explicit membership-sensitive projections and staff-only grants; `restaurant_has_feature()` remains an invoker wrapper. The existing `restaurant_can_write()` / `account_can_write()` boolean gates and pure `plan_features()` / `account_outlet_limit()` mappings remain operational helpers. Trial-grant and webhook-audit tables remain service-role-only. The migration and role probes were verified locally; no hosted database was queried or changed.

One separate execute-grant question remains open. `20261026001100_trial_plans_and_write_gate.sql` grants `restaurant_can_write(uuid)` to `anon`; `20261110001000_account_subscriptions.sql` revokes anon from the more revealing `account_can_write(uuid)` but leaves the restaurant-gate grant intact. The probe returns only a write/no-write bit, and `public_restaurant_profile()` exposes the restaurant UUID, so the UUID is not a secret. The only direct application RPC caller found is `lib/db/kitchen-screen.ts` for authenticated staff; no guest application component calls the probe directly. The latest SQL function-body callers are SECURITY DEFINER functions (including guest entrypoints such as `open_table_session` and the public-order path); their internal gate calls do not require anon execution. The final `restaurant_access()` definition is also SECURITY DEFINER and remains staff-only. The RLS dependency is different: `20261029000100_staff_invites.sql` creates gate-bearing `FOR ALL` policies without a `TO` clause (therefore applicable to `PUBLIC`) for `menus`, `categories`, `items`, `item_variants`, `item_addon_groups`, `item_addons`, `dining_tables`, and `qr_tokens`. The old `orders_staff_insert` policy was later dropped, and the surviving `orders_staff_update` policy is scoped to `authenticated`.

A local-only counterfactual on a fresh disposable embedded PostgreSQL replay of all **83 migrations** revoked `EXECUTE` on `restaurant_can_write(uuid)` from `PUBLIC` and `anon`. As expected, the direct guest probe failed with SQLSTATE `42501`; importantly, the guest menu/category/item RLS read also failed with `permission denied for function restaurant_can_write`. In the same isolated transaction, guest calls to `open_table_session` and `place_public_order_attempt` succeeded, confirming those SECURITY DEFINER RPCs do not need the anon grant. A direct anon read of the private table rows also failed at the RLS gate. The fixture transaction and disposable database were rolled back/destroyed. This demonstrates that the grant is not required by the guest RPC bodies, but is currently required by the active public-role RLS policy set to preserve supported guest menu reads. A standalone revoke would be a regression. No grant, policy, or test change was made, and no hosted Supabase/Vercel state was queried or changed. If an owner chooses to remove the boolean disclosure, a reviewed forward migration must first scope/refactor the gate-bearing management policies away from anon and then prove public menu/add-on reads, guest session/order flows, private-table isolation, and authenticated staff writes in disposable PostgreSQL/PostgREST tests.

The Cashier can still open the dashboard, but its staff context carries operational `entitlement` and `access: null`; therefore the dashboard does not render the commercial plan notice or its `Plans` / `Subscription` links. The navigation and subscription route also remain Owner/Manager-only. Owner/Manager dashboard presentation is unchanged.
