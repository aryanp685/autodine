# Phase 6C — Auth lifecycle hardening

**Evidence date:** 2026-11-06 UTC
**Branch / recorded base:** `arena/3878e9b8-autodine` / `e13720652440fc69280caa09e2e60bc151288426`
**Disposition:** Source and local unit/static/build checks completed. Supabase Auth, SMTP, Mailpit, browser PKCE, database replay, hosted configuration, and email delivery were **not** integration-tested. Staging remains **NO-GO**; Production remains **read-only**.

## Executive result

- Owner signup now uses a fixed `/auth/confirm?flow=signup&next=/dashboard` callback built only from a valid HTTPS request origin (HTTP is accepted only for loopback development). The origin parser rejects credentials, paths, query strings, and fragments. The callback destination is not caller-controlled.
- The server Auth client opts into Supabase's per-flow PKCE `sb_flow_id` callback parameter. Signup/resend persist the matching verifier through the SSR cookie adapter; `/auth/confirm` passes the callback flow ID to `exchangeCodeForSession`. Recovery's independent state-cookie check, reset-only authorization, safe redirect rules, and sign-out behavior are retained.
- A syntactically valid owner signup reaches the same confirmation-pending route whether Auth returns an identity-less enumeration-protected user, an Auth/provider error, or no user. Identity-less retries do not provision another workspace. A genuinely new signup still provisions its profile/workspace **before** email confirmation; that risk is unchanged and is documented below.
- The owner resend action calls `auth.resend({ type: 'signup' })`, but returns one generic `requested` state for every syntactically valid address, including Auth success, a 429, provider/Auth error, transport exception, or unavailable Auth client. Only malformed email input receives a different result. The UI therefore does not reveal whether an address is registered, confirmed, or mail-eligible, and it never claims delivery. Auth remains responsible for its actual send cooldown; there is no in-memory limiter or independent client timer.
- PKCE verifier deletion on resend/signup Auth errors is suppressed only for these enumeration-sensitive actions so cookie presence cannot distinguish a mail-eligible address. Tests verify the actual installed Supabase SSR/Auth client with mocked network responses. This is **unit-level library behavior**, not a real Auth/email/callback integration result.
- Confirmation-pending guidance covers inbox/spam, same-browser link use, retry cooldown, sign-in, and expired/reused links. The optional display-only email cookie is HttpOnly, SameSite=Lax, scoped to `/signup`, and expires after one hour. The form disables duplicate submissions while pending.
- Staff invitations were audited and left unchanged: single-use, expiring, revocable, manually shared links; confirmation remains a separate Auth step before redemption. The workspace/slug/trial risks were assessed without creating a cleanup or deletion policy.
- The source-level workspace write-gate audit found a P0 Staging blocker: authenticated owner/manager updates can likely change nullable `restaurants.account_id`, bypassing or remapping subscription entitlements. No SQL/policy fix was made in this Auth-only phase; a forward-only guard and disposable-DB/PostgREST regression test are required before Staging. The owner-unique-index/trial-claim comment was clarified at behavioral level; it is not a second-account path while the existing account row remains.
- Runtime investigation found no supported Docker/Podman/Nerdctl runtime. No privileged daemon was installed or started; the failed Phase 6B local Supabase start was not repeated. No hosted Auth setting, SMTP credential, DNS record, database, or email was read, changed, or used.

## Owner signup and confirmation lifecycle

1. `signUpAction` normalizes a bounded email address, validates the existing password and signup fields, and derives a fixed callback from `requestOrigin()` through `signupConfirmationRedirectTo()`.
2. The callback helper accepts HTTPS origins, or HTTP loopback only. It rejects a credential-bearing URL and any supplied path, query, or fragment, then fixes the route and destination to `/auth/confirm?flow=signup&next=%2Fdashboard`. The request-host source still depends on correctly trusted deployment proxy headers; syntactic origin validation is not a substitute for Supabase's redirect allowlist.
3. `lib/supabase/server.ts` configures `experimental.appendPkceFlowIdToRedirects`. The installed Auth client appends `sb_flow_id`; the server adapter persists the per-flow verifier, and the callback exchanges only against the matching flow when that parameter is present. The Supabase redirect allowlist must tolerate the additional query parameter (or use an appropriately constrained callback pattern). No hosted allowlist was inspected, so this remains a deployment prerequisite and the PKCE flow has not been verified against hosted Auth.
4. Valid-email Auth error/no-user responses route to the same pending screen as an identity-less duplicate. An identity-less response exits before profile/workspace provisioning. For a new identity, however, provisioning occurs before the action sees that `session` is absent and redirects to the pending screen. That is existing product behavior, not evidence that the email was delivered.
5. `resendSignupConfirmationAction` uses Supabase Auth only. It returns `invalid` for malformed input and the identical `requested` state for every valid address. It logs no recipient address or raw Auth/provider text; when Auth returns an error, only its status and code are written to server logs. The public result does not distinguish 429/provider failure from a request Auth accepted, and “requested” does not mean an email was sent or delivered.
6. `SignupConfirmationPendingScreen` lets the user edit the address if the display cookie is unavailable, gives neutral resend/cooldown guidance, and links to login. `AuthSubmit` disables the button while the Server Action is pending. There is no independent timer; Auth's configured limits remain the enforcement boundary.
7. On the callback, signup code-exchange or typed token-hash verification failures return to the pending screen with generic expired/reused-link guidance. Successful owner signup always lands at `/dashboard`, clears the display cookie, and does not trust a caller-supplied `next`. Other Auth callbacks continue to use the shared same-origin path validator. Recovery still requires the matching random `state` query and HttpOnly cookie for PKCE, successful exchange/typed recovery verification before the 15-minute recovery permission is issued, and the existing reset/sign-out safeguards.

The new PKCE test constructs the real `@supabase/ssr` server client and Auth SDK with a mocked `fetch`/cookie store. It verifies the resend body contains a challenge, the callback contains the corresponding `sb_flow_id`, the verifier is persisted, normal Auth error cleanup remains in place, and the enumeration-sensitive resend path keeps a uniform verifier-cookie shape on a 429. It does **not** send an email, reach a Supabase project, or prove browser cookie round-trip, redirect allowlisting, token validity, or email delivery.

## Staff invitation audit — behavior preserved

- `create_staff_invite` creates a 16-symbol code from a 32-symbol alphabet (80 bits); the database stores its SHA-256 hash rather than the plaintext. The SQL default is seven days and the function clamps requested expiry to 1–30 days. Owner/manager role limits apply; invitations cannot grant ownership.
- The invitation row has `expires_at`, `redeemed_at`/`redeemed_by`, and `revoked_at`. Preview requires a signed-in user. Redemption uses a row lock and checks active restaurant, revocation, prior redemption, expiry, and membership before writing. Existing membership does not consume a link. A retry by the same redeemer is idempotent only while that membership still exists; another actor sees the used status. The later P9 migration adds durable RPC attempt limits and this retry behavior.
- The invite is presented once through a short-lived HttpOnly Settings flash cookie and a copy-link UI. The product says no email is sent: the owner manually shares the link. A new staff account's separate Auth confirmation email returns to `/join/<code>`; membership is not granted until a signed-in user previews/accepts and the redemption RPC succeeds.
- Existing unit/source tests cover invite normalization/status copy, action refusal/rate-limit handling, cookie/manual-share behavior, and P9 migration text. No migration was replayed, so SQL locking, expiry timing, and membership effects were not executed against a database in this phase.

### Workspace write-gate audit outcome

- The final subscription gate is account-level: `account_can_write` rejects expired accounts, accepts a running trial, and allows paid/cancelled/past-due states only under the effective period rules in the billing migration. Every outlet linked to that account receives the same result through `restaurant_can_write`.
- RLS/RPC checks apply that subscription gate to the main licensed writes (menus, categories, items and related variants/add-ons, dining tables/QR tokens, invitation operations, staff order progress, and order/payment/session operations). Public ordering additionally checks storefront/table active state. This is a source audit; none of these policies or function bodies was executed against a database in Phase 6C.
- Deliberate recovery exceptions remain: owner/manager restaurant details, tax/guest-verification settings, branding assets and brand drafts may be changed independently of billing so an expired workspace can correct or recover its records. Brand/menu publishing and ordinary licensed writes still call the gate. These exceptions mean “read-only” is a billing-feature mode, not literally zero database writes.
- The account-link mutability finding above is the release-critical gap: the policy/trigger combination does not currently enforce that entitlement association against authenticated updates. It can null or redirect the link before the gate resolves.
- The anon boolean probe is preserved by existing grants and an integration-test expectation; its acceptability is a separate product/security decision, not evidence that Auth or database integration passed.

A same-email enumeration-protected retry is deliberately different from a new identity internally: it goes to the same generic pending screen but exits before workspace creation. This prevents a duplicate workspace/trial for that response shape; it does not solve abandoned first-time signup state.

## CAPTCHA and Auth rate-limit requirements

The official Supabase Auth CAPTCHA guide documents hCaptcha and Cloudflare Turnstile. Its integration requires a frontend challenge token passed to Auth in the `captchaToken` option and the corresponding provider secret configured in Auth's Bot and Abuse Protection settings. No provider or secret is selected here; no CAPTCHA UI/token forwarding is present in the current signup/resend path. An implementation decision must cover signup and relevant sign-in/reset flows, failure/expiry behavior, accessibility, and an authorized secret-configuration process.

Supabase Auth rate limits are configurable (including email-send and OTP limits); the official guidance describes 429 responses and IP-based token-bucket limits. OTP request frequency/validity are configuration-dependent. No hosted project values were read, and documentation examples are not evidence of AutoDine settings. The resend UI deliberately does not expose a per-address rate-limit result; Auth remains the enforcement source. No in-memory limiter or weakened Auth protection was introduced.

References: [Supabase CAPTCHA protection](https://supabase.com/docs/guides/auth/auth-captcha), [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits), and [Auth email passwordless/OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless).
