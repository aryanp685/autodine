## What changed

- **Scan, verify, then order.** Live card admission and code/session limits remain in place. A limited scan can browse but clears stale table authority. Code confirmation does not submit an order. The database controls outlet, table, menu availability and pricing in paise. The forward wrapper refuses a partial basket atomically and replays a committed attempt only at the same live table after re-verification. There is no order-submission budget.
- **Keep the original attempt.** Checkout saves a scoped UUID, basket and note before sending. In the same browser, Web Locks serialize attempts; absent usable locking or recovery storage, offer staff help rather than start an untracked write. An acknowledged result consumes only the submitted cart if it still matches. A status link or old confirmation never clears it. Guest status returns only the scoped, minimal non-cacheable view; prep and payment progress separately.
- **Record, do not charge.** Counter staff verify cash, external card or external UPI, then record the exact ticket, method and outstanding paise. The recording attempt survives a lost response and reload. An already-paid, missing or amount-changed ticket can be checked against the original ledger entry without recording anything. Another method or another ticket is not confirmation. The separate staff-manual settlement stays manual, not a named tender or a gateway. Online guest payments and subscription billing did not change.
- **Close, then issue.** The final numbered document comes from authorized sitting close and saved invoice, line and tender snapshots, not the guest status page. A usual pre-close payment is in that snapshot; it is not a separate supplemental acknowledgement. Browser/OS print is supported. Only eligible ordinary receipts may receive an expiring, revocable share; an identified delivery or an IRN-held document is not made public. GST/IRP amounts, activation and legal-release decisions were not changed.
- **Bound errors.** A refusal can name a known business reason or a bounded error class. Unexpected driver text is not reflected in checked screens or redirects. The runner rejects selected synthetic private markers in application logs. This is not evidence about all log sinks or hosting access logs.

## Browser evidence and persisted assertions

The production Next build ran with Chromium phone emulation (390×844) and desktop (1280×900). The fixture adapter implements only the called HTTP shapes; each business request executes as the real `anon` or `authenticated` PostgreSQL role. The fresh journey/native runner uses the existing local Supabase shim and legacy table scaffold, not a clone of the hosted schema. The disposable DB administrator seeds fixture configuration and models time boundaries or a filled scan budget, but does not seed business outcomes to make tests pass. The scopes tested:

| Case | Observed result |
|---|---|
| Phone: code → customized basket | A wrong code produces no order; after the in-venue code, two Large thalis with extra curd, rice and the guest note persist in a single ticket for **₹352.43** (inclusive GST **₹16.78**). The order reply is lost *after commit*. After expiry, reload and reverification, the same attempt returns the same ticket, with no duplicate or lingering matching cart. |
| Phone: kitchen → UPI → GST invoice | New → preparing → ready → served while payment is still pending. A dropped database reply on external UPI is reconciled as **one** recorded ₹352.43 tender and one audit event. Guest polling reaches paid; staff close saves an issued GST invoice with the same total, tax and payment snapshot, visible in print media. Wrong outlet cannot open the staff invoice. |
| Anonymous receipt link | The same saved number and amount are presented without staff controls. Link issue failure is safe and does not create a row. Revocation makes it unavailable on reload; a second link's saved lifetime is **86,400 seconds** and forced fixture expiry refuses the document. A kitchen-only role and another outlet cannot use private bill access. |
| Desktop: scan-and-confirm → cash → plain receipt | Table B1's ticket waits outside the normal kitchen queue until staff confirm. A response is dropped after the cashier records **₹105.11 cash**. From the unfocused queue, the action pins this exact ticket; Back/reload recovers the original payment with a read-only check. One tender/audit row, no pre-close invoice, a paid private bill, then **one** issued plain receipt with no CGST and print visibility. |
| Counter interrupted before write | A lost pre-query Card recording preserves the original **₹42.01**, method and attempt through reload. The retry records one Card tender; it does not substitute the default cash method. The identified same-state delivery's saved receipt remains private; a cross-state attempt is refused and produces no ticket. Takeaway also runs through staff-only creation and is visible in the active sitting list. |
| Counter stale/concurrent/browser limits | A quantity change raises a still-open ticket from ₹42.01 to ₹84.02; the old amount is refused, and check-only retry adds no payment. A same-origin competing tab cannot send a second recording or change the tender while the first is held. For a now-paid ticket the original Card attempt is *not* confirmed by an equal Cash entry from another terminal. Missing Web Locks and blocked storage writes result in zero tenders. |
| Checkout isolation and replay | No direct menu access without a card; inactive/revoked cards cannot write. A stale tab cannot place against another table's session. Wrong-code and scan budgets mint no new usable session, but the menu/cart remain browseable when applicable. Same-browser competing checkout and transient refusal yield one saved ticket. A changed cart survives reconciliation, a bookmarked old confirmation and Back/reload. Corrupt storage and no Web Locks refuse submission. |
| Guest/status/ledger privacy | Wrong-outlet, random and malformed status credentials return no order; the successful payload contains just minimal status fields and `no-store`. Guest edit and staff ledger faults show safe copy/reference, not the synthetic driver diagnostic. No tested application-log canary was exposed. |

These cases test screen behavior and saved rows, not a physical payment terminal, a printer, an OS sharing sheet or device cameras. Kitchen speech transport was intentionally blocked. The app remains responsible for authorized counter recording, not detection of tender in a real terminal.
